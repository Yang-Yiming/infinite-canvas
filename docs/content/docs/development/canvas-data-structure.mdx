# Canvas Data Structure

## Storage

Canvas projects and My Assets are stored with localForage in the `infinite-canvas` database and `app_state` store. Image blobs use `image_files`; other media blobs use `media_files`. Project JSON stores display URLs, `storageKey`, and metadata rather than large base64 payloads.

## Project

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  viewport: { x: number; y: number; k: number };
  script: CanvasScriptEntry[];
};
```

The viewport stores screen translation in `x` and `y`, and scale in `k`. `script` is the script console history described under Script console data.

## Nodes and edges

```ts
type CanvasNodeData = {
  id: string;
  type: "image" | "text" | "config" | "video";
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
};
```

Node positions and sizes use canvas-world coordinates. Edges store only node IDs; their paths are calculated while rendering. Deleting a node removes its connected edges.

Common metadata includes content, prompt, status, generation mode, model, size, count, natural dimensions, image results, input order, `storageKey`, MIME type, byte size, and for in-progress OpenAI-style videos a `videoTaskId` used to resume status polling after refresh. A multi-image generation remains one image node: `images` creates all requested slots before generation starts and records each slot's `status`, `errorDetails`, and completed image data. `primaryImageId` selects the result mirrored by the node-level `content` and image metadata; the first successful slot becomes primary immediately. Persisted image and video `content` values are normally session-scoped `blob:` URLs, with `storageKey` as the persistent identity. If CORS prevents reading an otherwise displayable image, `content` may remain a potentially expiring remote URL and `storageKey` is omitted.

Two metadata fields belong to the script console: `alias` is the variable name assigned to the node and must be unique within a canvas, and `script` keeps the statement that generated the node so `name!` can rerun it. Nothing else reads or writes them, and deleting the node invalidates the variable.

## Script console data

The console keeps no state of its own: variables are node `metadata.alias` values, and only the execution history is persisted on the project.

```ts
type CanvasScriptEntry = {
  id: string;
  source: string;
  nodeIds: string[];
  status: "running" | "success" | "error";
  error?: string;
  output?: string;
  createdAt: string;
};
```

- `source`: the original statement, refilled into the editor when the entry is clicked.
- `nodeIds`: nodes produced or bound by that statement, used for thumbnails and for re-judging status after a reload.
- `status` / `error` / `output`: execution state, failure reason, and the text printed by `:ls` and `:help`.
- `createdAt`: ISO string.

In-flight generations live in memory only (a `pending` map) and are never written to the project. After a reload, entries still marked `running` are re-judged from the current status of their `nodeIds`.

Snippets (`:def`) expand the same way: a snippet is a parameterised text macro that is re-parsed as an ordinary statement and never added to project data. The snippet library lives in browser storage (`infinite-canvas:canvas_script_snippets`) and is not included in canvas export or sync.

## Assistant sessions

```ts
type CanvasAssistantSession = {
  id: string;
  title: string;
  messages: CanvasAssistantMessage[];
  createdAt: string;
  updatedAt: string;
};
```

Message references and generated images use the same blob-storage rules. They are converted to data URLs temporarily only when an AI endpoint requires base64.

## Media lifecycle

`uploadImage()` accepts a Blob, data URL, or remote URL. It downloads remote data once, verifies that the Blob decodes as an image, stores it in `image_files` under an `image:<id>` key, and returns an in-memory object URL plus metadata. If CORS blocks byte access but the browser can still display the remote image, it returns that URL without a storage key. Opening a project resolves each stored key into a fresh object URL.

Cleanup is reference-based. After deleting nodes, canvases, assets, or assistant sessions, the application collects every still-referenced storage key, removes unreferenced blobs, revokes their object URLs, and removes them from the in-memory cache. This prevents deleting a file still shared by another canvas feature.
